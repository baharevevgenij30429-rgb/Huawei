# План работы команды 521

Цель первого этапа: воспроизводимый контейнер, который решает восемь примеров
через разрешённый API, сохраняет ответы и измеряет расход. Это ориентир команды,
не утверждение о текущем качестве прототипа.

## Участник 1 — инфраструктура и агент

Ветка: `feature/infrastructure`.

- Выделить из run_agent.py модули client.py и tools.py без изменения поведения.
- Проверить совместимость openjiuwen==0.1.19 с прокси: модель, JSON, таймауты,
  реальные поля usage и включение токенов рассуждений.
- Собрать Docker, проверить запуск с read-only корнем и запись в mount задач.
- Зафиксировать транзитивные зависимости после успешной сборки; проверить
  размер образа меньше 4 ГБ и время сборки меньше 1000 секунд.
- Усилить изоляцию инструментов, защитить тесты от изменений и завершать
  дочерние процессы при таймауте.

Готово, когда: образ собирается с нуля, одна задача проходит API-цикл, answer.txt
остаётся после завершения контейнера, ключи отсутствуют в файлах и логах.

## Участник 2 — планировщик и бюджет

Ветка: `feature/planner`.

- Выделить priority и бюджет в planner.py и budget.py после согласования
  границ с участником 1.
- Использовать reward, тип, длину инструкции, размеры доступных файлов,
  результаты предыдущих шагов; исключить expected/check из признаков.
- Собирать прогноз стоимости и вероятности успеха, сравнивать с baseline.
- Добавить лимит расхода на задачу и правило прекращения повторных попыток.
- Проверить переключение между разрешёнными моделями на одинаковых задачах.
- Параллелизм добавлять после корректного общего резервирования бюджета.

Готово, когда: на отдельном контрольном наборе можно сравнить баллы и расход
при одинаковом бюджете; запросы не стартуют без доступного резерва; задачи
с отсутствующими данными не вызывают бесконечные попытки.

## Участник 3 — данные, проверка и воспроизводимость

Ветка: `feature/evaluation`.

- Создать evaluate.py: запуск на копии задач и независимая проверка ответов.
- Уточнить официальный путь answer.txt; для coding проверять тесты и
  неизменность исходных test-файлов, а не только слово DONE.
- Собрать свои задачи четырёх типов, включая недостающие данные и
  противоречивые условия. Разделить тренировочный и контрольный наборы.
- Сохранять task id, модель, фактический расход, время, шаги, статус проверки
  и баллы; ключи в траектории не включать.
- Подготовить таблицу сравнения вариантов и раздел README о траекториях.

Готово, когда: повторный запуск даёт проверяемый отчёт по всем восьми примерам,
оценщик обнаруживает неправильный ответ, провал тестов и изменение тестов;
контрольные эталоны недоступны решателю.

## Совместная последовательность

1. Уточнить у организаторов путь ответов, размер/передачу бюджета, CPU и дедлайн.
2. Участник 1 подтверждает один API-вызов; участники 2 и 3 параллельно готовят
   планировщик и оценщик без API.
3. Общий прогон восьми примеров: сначала correctness, затем расход.
4. Сравнить варианты на собственном контрольном наборе, исправить регрессии.
5. Проверить квалификационный сценарий из двух выполнимых задач и финальный
   Docker-запуск; заморозить рабочую версию до дедлайна.

## Как работать в Git

Каждый делает отдельную ветку и pull request. Перед слиянием другой участник
читает изменения и запускает `python -m unittest -v test_baseline.py`.
Изменения API модулей согласовывайте в описании PR. В main держите запускаемую
версию. Ключ передавайте через окружение, не через чат PR, issue или коммит.

GitHub-логины участников пока не заданы: роли закрепляются командой;
этот документ не назначает доступ и не отправляет приглашения.
